# 技术栈说明

## 项目名称

个人网站 / 技术博客

当前包含三个主要模块：

```text
About
Projects
Blog
```

项目第一阶段目标是完成基础全栈业务功能。

**当前阶段：纯前端。**

先完成 About / Projects / Blog 的前台页面（UI、路由、响应式、动画），
数据暂时使用静态数据（写死或本地 JSON / TS 常量），
暂不接入数据库、认证和后端逻辑。

数据库、Auth.js、Tiptap 等属于后续全栈阶段（见各章节标注）。

当前阶段不引入复杂的基础设施和微服务架构。

Docker、CI/CD、Kubernetes、监控等将在后续版本中逐步加入。

---

# 一、核心技术栈

## 1. 全栈框架

### Next.js

使用 Next.js 作为项目唯一的主框架。

负责：

* 前端页面
* 路由
* 服务端渲染
* Server Components
* Server Actions
* Route Handlers
* 基础后端业务逻辑

当前项目采用：

```text
Next.js Fullstack Monolith
```

即：

```text
Browser
    │
    ▼
Next.js
├── UI
├── Server Components
├── Server Actions
└── Route Handlers
    │
    ▼
Business Logic
    │
    ▼
PostgreSQL
```

第一阶段不引入 NestJS、FastAPI 或其他独立后端服务。

后续如出现 AI、OCR、异步任务、数据处理等特殊需求，可以拆分独立服务。

---

## 2. 编程语言

### TypeScript

项目统一使用 TypeScript。

要求：

* 尽可能保持完整的类型定义
* 避免使用 `any`
* 公共数据结构定义明确的 Type
* 函数参数和返回值保持合理的类型约束

# 二、UI 技术栈

## 1. CSS 框架

### Tailwind CSS

负责：

* 页面布局
* 响应式设计
* 间距
* 字体
* 颜色
* 动画
* 自定义样式

项目统一使用 Tailwind CSS。

不额外引入其他大型 CSS 框架。

当前项目使用 Tailwind CSS v4（通过 `@tailwindcss/postcss` 接入，CSS 变量主题配置方式，无 `tailwind.config.js`）。

注意：v4 与旧版（v3）的配置方式差异较大，参考教程时需注意版本。

* 业务逻辑和数据访问逻辑保持适当分离

# 六、服务端架构（后续全栈阶段）

> 当前阶段为纯前端，暂无 Server Actions / Route Handlers / 分层架构，页面直接使用静态数据渲染。
> 以下为后续全栈阶段的分层方案，前端阶段写组件时避免把展示和数据来源写死耦合，方便后续替换。

项目当前采用单体全栈架构。

业务逻辑建议分层：

```text
UI / Page
    │
    ▼
Server Component
Server Action
Route Handler
    │
    ▼
Service
    │
    ▼
Repository
    │
    ▼
Prisma
    │
    ▼
PostgreSQL
```

职责划分：

## Page / Component

负责：

* 页面展示
* 用户交互
* 调用服务端逻辑

不负责：

* 复杂业务逻辑
* 大量数据库操作

---

## Server Actions

主要用于：

```text
表单提交
创建数据
修改数据
删除数据
```

例如：

```text
创建文章
修改文章
删除文章
创建项目
修改项目
```

---

## Route Handlers

仅用于确实需要 HTTP API 的场景。

例如：

```text
/app/api/*
```

后续可能用于：

```text
第三方服务调用
Webhook
外部 API
FastAPI 服务通信
其他客户端调用
```

不要求所有 CRUD 都创建 REST API。

---

## Auth.js（NextAuth）（后续全栈阶段）

管理员认证统一使用 Auth.js。

负责：

* 管理员登录 / 登出
* 会话管理
* 后台管理接口的访问控制

原则：

* 仅管理员需要登录，前台页面匿名访问
* 认证逻辑集中在服务端，不在页面组件中散落判断

## Service Layer

负责：

* 业务逻辑
* 数据处理
* 业务规则
* 协调 Repository

例如：

```text
services/
├── post.service.ts
├── project.service.ts
└── about.service.ts
```

---

## Repository Layer

负责：

* 数据库访问
* Prisma 查询
* 数据持久化

例如：

```text
repositories/
├── post.repository.ts
├── project.repository.ts
└── user.repository.ts
```

# 七、内容系统（后续全栈阶段）

> 当前阶段为纯前端，文章/项目内容直接用静态数据展示。
> 以下为后续接入时的方案（已确认）：

博客文章正文存储方案（已确认）：

```text
PostgreSQL，Post.content 字段存 HTML
```

* 编辑器使用 Tiptap，输出 HTML
* HTML 在入库/渲染前必须经过 Sanitization（如 `sanitize-html` / `isomorphic-dompurify`），防止 XSS
* 图片只存 URL，不存文件本体；对象存储后续接入
* Tiptap 需支持：代码块、代码高亮、表格、图片（URL）、引用、任务列表

# 九、后续扩展能力

项目需要保持可扩展性。

未来可能变成：

```text
Next.js
    │
    ├── PostgreSQL
    │
    ├── FastAPI
    │     ├── AI
    │     ├── OCR
    │     ├── 数据处理
    │     └── 异步任务
    │
    └── Other Services
```

因此要求：

* 页面层不要直接耦合数据库
* 业务逻辑尽量集中在 Service Layer
* 数据访问集中在 Repository Layer
* 对外服务通过 HTTP API 或其他明确接口通信
* 不提前设计无实际用途的微服务架构

原则：

> 当前保持简单，但避免把业务代码和 UI、数据库完全耦合在一起。

# 十一、开发环境与工程约定

## 本地数据库（后续全栈阶段）

> 当前纯前端阶段无需数据库，以下为后续全栈阶段的本地开发方案。

本地开发使用 Docker 运行 PostgreSQL：

```bash
docker run --name aboutme-postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=aboutme \
  -p 5432:5432 -d postgres:17
```

注意：Docker 仅用于本地开发环境，不属于部署架构（部署阶段的基础设施后续再定）。

## 环境变量

* 当前纯前端阶段暂无必需变量
* 后续全栈阶段：使用 `.env.local` 存放本地敏感配置（不提交仓库），提供 `.env.example` 作为模板（提交仓库）
* 届时必需变量：`DATABASE_URL`，以及 Auth.js 相关（`AUTH_SECRET` 等）

## 格式化与 Lint

* 代码格式化：Prettier
* Lint：保留 Next.js ESLint（`eslint-config-next`）
* 两者配合使用，Prettier 管格式、ESLint 管代码质量
